01 · Overview

Two Ideas. One Module.

In Transformer models, attention allows each token to look at other tokens and decide which ones are important. Two mechanisms power this:

⏮

Causal Attention

Prevents any token from looking into the future. Enforces the direction of time during autoregressive generation.

🔀

Multi-Head Attention

Splits the representation into subspaces so the model can learn multiple similarity metrics in parallel.

02 · Input

From Embedding to Keys, Queries, Values

Everything starts from an input tensor x:

# x : (batch, num_tokens, d_in)

keys    = self.W_key(x)    # → (b, num_tokens, d_out)
queries = self.W_query(x)  # → (b, num_tokens, d_out)
values  = self.W_value(x)  # → (b, num_tokens, d_out)

# d_out = num_heads × head_dim

Three linear projections, each producing d_out = num_heads × head_dim features.

03 · Splitting Heads

Reshape, Then Transpose

We want each head to operate independently. This takes two steps:

# Step 1 — view: reinterpret memory layout
keys = keys.view(b, num_tokens, num_heads, head_dim)
# (b, num_tokens, num_heads, head_dim)

# Step 2 — transpose(1,2): move head dim forward
keys = keys.transpose(1, 2)
# (b, num_heads, num_tokens, head_dim)
#     ↑ now: Batch → Head → Token → Feature

After transpose(1, 2), each head has its own slice of the batch dimension. Attention computation per head becomes clean and parallelisable.

04 · Attention Scores

Why keys.transpose(2, 3)?

Matrix multiplication demands inner dimensions to match: (..., m, k) @ (..., k, n). After splitting heads we have:

queries: (b, num_heads, num_tokens, head_dim)
keys:    (b, num_heads, num_tokens, head_dim)

# ❌  (num_tokens, head_dim) @ (num_tokens, head_dim) — invalid
# ✅  (num_tokens, head_dim) @ (head_dim, num_tokens) — valid

attn_scores = queries @ keys.transpose(2, 3)
# keys after transpose: (b, num_heads, head_dim, num_tokens)
# result:               (b, num_heads, num_tokens, num_tokens)

transpose(2, 3) is purely a linear algebra requirement — nothing more, nothing less.

05 · Causal Masking

Blocking the Future

When predicting token i, the model must not see tokens at positions > i. We enforce this with an upper-triangular mask:

self.register_buffer(
    "mask",
    torch.triu(torch.ones(context_length, context_length), diagonal=1)
    # 1 = forbidden   0 = allowed
)

# Apply: replace forbidden positions with -∞
attn_scores.masked_fill_(mask_bool, -torch.inf)

# After softmax: softmax(-∞) = 0 → future tokens get weight 0

06 · register_buffer

Why Not Just self.mask = …?

If you assign the mask as a plain attribute, calling model.to("cuda") moves parameters to the GPU — but your mask stays on CPU, causing a device mismatch error. register_buffer solves all three problems at once:

🚀

Moves with model

Automatically transferred when you call .to(device) or .cuda().

💾

Saved in state_dict

Persists when you checkpoint and reload the model.

🔒

Not learnable

No gradient, no optimizer update. It's a fixed architectural rule.

07 · Context Vector

Merge the Heads Back

After weighted aggregation over values, we need to reassemble the multi-head output:

# Weighted sum over values
context_vec = attn_weights @ values
# (b, num_heads, num_tokens, head_dim)

# Put token dim back before head dim
context_vec = context_vec.transpose(1, 2)
# (b, num_tokens, num_heads, head_dim)

# Merge heads: concatenate along last two dims
context_vec = context_vec.view(b, num_tokens, d_out)
# (b, num_tokens, d_out)   where d_out = num_heads × head_dim
08 · Shape Flow

Every Transform, In Order

Input → (b, num_tokens, d_in) raw embeddings
Linear → (b, num_tokens, d_out) W_q / W_k / W_v
view → (b, num_tokens, num_heads, head_dim) split heads
transpose(1,2) → (b, num_heads, num_tokens, head_dim) head first
@ keys.T(2,3) → (b, num_heads, num_tokens, num_tokens) attention scores
softmax → (b, num_heads, num_tokens, num_tokens) attention weights
@ values → (b, num_heads, num_tokens, head_dim) context per head
transpose(1,2) → (b, num_tokens, num_heads, head_dim) token first again
view → (b, num_tokens, d_out) merge heads
09 · Quick Reference

The Two Transposes

Operation Reason Shape change
transpose(1, 2) Rearrange tensor so heads lead, enabling per-head view & final reshape (b, T, H, D) → (b, H, T, D)
transpose(2, 3) Satisfy matrix multiplication inner-dimension rule for QKᵀ (b, H, T, D) → (b, H, D, T)

Nothing mystical. One is for tensor layout; the other is for linear algebra.

10 · Misconceptions

Common Confusions — Resolved

✗ False
"Transpose changes the data." No. It only reorders the axes. The underlying memory values are untouched.
✗ False
"view() splits the tensor into separate pieces." No. It reinterprets the existing memory layout without any copy or split.
✗ False
"The causal mask is a learnable parameter." No. It's a fixed architectural rule registered as a buffer, with no gradient.
✗ False
"Multi-head attention means multiple separate models." No. It means splitting a single representation into parallel subspaces within one module.
11 · Tip

Debug Shapes Like a Pro

When attention code confuses you, follow this four-step method:

# 1. Write down the current shape
print(tensor.shape)

# 2. Write the matmul rule: (..., m, k) @ (..., k, n)
# 3. Find which dimensions need to align
# 4. Ask: is this transpose for math compatibility or for reshaping?

Master shape tracking → master attention. It really is that simple.
